# QUAL-044設計プロセス：長時間処理キューシステムの技術的検討（Phase 1）

## 📌 背景

Claude Code使用時に発生する2分タイムアウト制約により、pytest（全テスト）やextract_character.py（バッチ処理）等の長時間処理が中断される問題を解決するため、キューベースの長時間処理システムの設計を検討した。

## 🎯 ユーザー要件定義

### 初期要求
- **対象処理**: pytest（全テスト）、extract_character.py
- **キューシステム**: FIFO（先入先出）
- **通知方法**: コスト分析要求、Pushoverが第一候補
- **エラーハンドリング**: 自動リトライ（2回）→TaskFailureEscalation→ユーザー通知
- **進捗監視**: コスト分析要求
- **処理中断・再開**: 全機能必要
- **システム適用範囲**: 全ての長時間処理（将来拡張性）

### 詳細要件（Q&A形式）
```
Q: 対象となる長時間処理は？
A: pytest（全テスト）、extract_character.py この２つ

Q: キューの優先度管理は？
A: FIFOでOK

Q: 通知方法の希望は？
A: tokenが少ない方が良いので一度リストアップして判断させて

Q: エラー処理方針は？
A: 自動リトライ→TaskFailureEscalation→ユーザー通知の流れ

Q: システム適用範囲は？
A: 全ての長時間処理対象 今後も長い処理が来たらこのシステムを利用したい
```

## 🚨 重要な技術的制約の発覚

### Pushover-Claude自動連携の限界

**ユーザーからの重要な質問**:
> 質問：Pushoverで通知 -> Claudeがそれを受け取り次の行動に移ってくれるのですか？Pushoverでそういうことが実現可能でしょうか？

#### Pushover API制約分析
- **送信のみ**: 通知をデバイスに一方向送信
- **受信確認**: 通知の既読確認のみ（アクション実行不可）
- **双方向通信**: サポートなし
- **Webhook**: なし（受信時のコールバック不可）

#### Claude Code側の制約
- **外部トリガー受信**: 基本的にサポートなし
- **常時起動**: 必要時のみ起動するCLIツール
- **API待機**: WebSocket/HTTPサーバー機能なし

### 修正されたアーキテクチャ（第1回）

**結論**: Pushover → Claude自動連携は技術的に実現困難

```
┌─────────────────┐    ┌──────────────────┐    ┌──────────────┐
│   Queue System  │───▶│   Status File    │◄───│ Claude Monitor│
│                 │    │ (JSON/完了通知)   │    │ (定期チェック) │
└─────────────────┘    └──────────────────┘    └──────────────┘
         │                                              │
         ▼                                              ▼
┌──────────────────┐                          ┌──────────────┐
│     Pushover     │                          │  Next Action │
│ (ユーザー通知のみ) │                          │  Execution   │
└──────────────────┘                          └──────────────┘
```

## 🔄 コンテキスト分離の根本的問題

### セッション分離問題の発覚

**ユーザーからの核心的な質問**:
> これは現在表示されてる会話セッションとは別セッションでClaude Codeが起動してClaudeCodeの対話が始まるのですか？それとも同一セッションですか？

#### 技術的現実の確認

**現在のセッション（この会話）**:
```bash
# ユーザーが最初に実行
claude code
# → この対話セッションが開始（セッションA）
```

**シェルスクリプトからの呼び出し**:
```bash
# auto_monitor.sh内での実行
claude code --prompt "queue_status.jsonを確認して..."
# → 新しい別セッション起動（セッションB）
```

#### セッション分離の深刻な影響

**セッション A（現在の会話）**:
- この会話の文脈・履歴を保持
- ユーザーとの継続的な対話
- `auto_monitor.sh` の実行は認識しない

**セッション B（自動起動）**:
- 全く新しいコンテキスト
- セッションAの履歴なし
- 独立した判断・実行
- 終了後はセッションAに影響なし

### コンテキスト分離による問題例

```
セッションA: "QUAL-044を実装中です"
          ↓ (auto_monitor.sh実行)
セッションB: "何のプロジェクトですか？履歴が見えません"
```

#### 状態管理問題
- セッションBは現在の作業状況を認識しない
- Todo list、進捗、計画の共有なし
- 重複作業や矛盾した判断の可能性

### 限界の明確化

**実現可能性の再評価**:

| アプローチ | セッション継続性 | 文脈保持 | 実装複雑度 | 推奨度 |
|-----------|----------------|---------|-----------|--------|
| **通知+手動継続** | ✅ 同一 | ✅ 完全 | 低 | ⭐⭐⭐⭐⭐ |
| **ファイル状態共有** | ❌ 別 | △ 部分的 | 高 | ⭐⭐ |
| **別セッション自動** | ❌ 別 | ❌ なし | 中 | ⭐ |

## 💡 サブエージェント技術による解決案

### 技術的ブレークスルー

**ユーザーからの決定的な質問**:
> 私が望んでるのはコンテキストが分離せず同一セッションなのですが例えばAnthropicのサブエージェント https://docs.anthropic.com/ja/docs/claude-code/sub-agents でも困難ですか？

### サブエージェント技術の優位性

#### **同一セッション内での動作**
```python
# 現在のセッション（この会話）内で
<invoke name="Task">
<parameter name="subagent_type">general-purpose</parameter>
<parameter name="description">Queue status monitoring</parameter>
<parameter name="prompt">
queue_status.jsonを監視して、完了時に次のアクション（pytest実行）を実行してください。
現在の作業文脈：QUAL-044長時間処理キューシステム実装中
</parameter>
</invoke>
```

#### **コンテキスト継承の利点**
- ✅ **同一セッション**: この会話の文脈を完全保持
- ✅ **Todo継承**: 現在のTodoリストを継承
- ✅ **作業状況認識**: QUAL-044の進捗状況を理解
- ✅ **プロジェクト理解**: segment-anythingプロジェクトの構造理解済み

### 革新的アーキテクチャ設計

#### **Queue + SubAgent システム**
```
┌─────────────────┐    ┌──────────────────┐    ┌──────────────┐
│  Long Task      │───▶│   Status File    │───▶│  SubAgent    │
│  (pytest)       │    │ (queue_status.json)│   │ (同一セッション)│
└─────────────────┘    └──────────────────┘    └──────────────┘
                                                        │
┌─────────────────┐    ┌──────────────────┐             ▼
│    Pushover     │◄───│  Main Session   │◄────┌──────────────┐
│   Notification  │    │ (この会話継続)     │     │ Next Action  │
└─────────────────┘    └──────────────────┘     │  Execution   │
                                                └──────────────┘
```

#### **実装の流れ**
1. **Queue開始**: 長時間処理（pytest）をバックグラウンド実行
2. **SubAgent監視**: 同一セッション内でサブエージェントがstatus file監視
3. **完了検出**: サブエージェントが完了を検出
4. **コンテキスト保持**: この会話の文脈を持ったまま次アクション実行
5. **Pushover併用**: ユーザーへの通知も並行実行

### 技術的優位性の確認

| 項目 | 従来案（別セッション） | サブエージェント案 |
|-----|-------------------|------------------|
| **コンテキスト** | ❌ 分離・消失 | ✅ 完全継承 |
| **Todo管理** | ❌ 引き継げない | ✅ 同一リスト |
| **作業状況** | ❌ 不明 | ✅ QUAL-044継続 |
| **プロジェクト理解** | ❌ ゼロから | ✅ 既存知識活用 |
| **実装複雑度** | 中（状態ファイル） | 低（標準機能） |
